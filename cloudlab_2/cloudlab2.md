# Лабораторная работа 2: Сравнение сервисов AWS и Microsoft Azure. Создание единой кросс‑провайдерной сервисной модели

## Цель работы

1) Получение навыков аналитики и понимания спектра публичных облачных сервисов без привязки к вендору.  
2) Формирование кросс‑провайдерной сервисной модели (vendor‑neutral), позволяющей анализировать потребление от общего уровня к частному, сохраняя принципы классификации из ЛР1.

## Исходные данные

В качестве исходных данных использовался слепок биллинга Microsoft Azure (Azure lab team 9.csv).  
Для идентификации сервисов применялись поля биллинга:

- Meter Category
- Meter Sub‑Category
- Meter Name
- Consumed Service

Часть значений содержит шаблоны с использованием символа `%`, означающего произвольную последовательность символов.

## Ход работы

CSV‑файл был импортирован в табличный редактор. Далее строки биллинга Azure были сопоставлены с документацией провайдера и классифицированы по иерархии сервисов, совместимой с моделью ЛР1.

Для каждой строки были заполнены следующие поля сервисной модели:

- IT Tower
- Service Family
- Service Type
- Service Sub Type
- Service Usage Type

### Принципы классификации (согласованно с ЛР1)

Классификация выполнялась от общего уровня к частному:

**IT Tower → Service Family → Service Type → Service Sub Type → Service Usage Type**

При этом:

- **IT Tower** использовался как верхний уровень группировки (Compute / Network / Cloud Services / Support).
- **Service Family** уточнял направление внутри башни (например, Compute / Network / Application Services / Content Delivery / Support).
- **Service Type** задавал человекочитаемое имя сервиса в стиле ЛР1 (например, *Azure Container Instances*, *Azure Application Gateway*).
- **Service Sub Type** фиксировал подтип/режим/ SKU (например, *SKU: Standard v2*, *CPU*, *Memory*, *Data transfer*).
- **Service Usage Type** фиксировал конкретный тарифный метр (например, *Gateway capacity units*, *vCPU time*, *Transactions*).

### Особые случаи

- Метры категории **Bandwidth** трактовались как сетевое потребление (*Network*), но **Service Type** привязывался к потребляющему сервису (например, *Azure Machine Learning*, *Azure Cognitive Search*), чтобы расходы на трафик корректно агрегировались по сервисам.
- Финансовые строки, не являющиеся прямым потреблением ресурсов (налоги/подписки/разовые платежи), при наличии должны выделяться отдельно аналогично ЛР1.

## Результаты

В результате была получена структурированная таблица Azure‑биллинга, в которой каждая строка однозначно классифицирована по единой сервисной модели.  
Это позволяет выполнять анализ потребления сверху вниз: от IT Tower до конкретного типа использования.

## Вывод

В ходе работы были закреплены навыки чтения облачного биллинга Azure и сопоставления строк потребления с документацией провайдера.  
Также была сформирована кросс‑провайдерная сервисная модель, согласованная с ЛР1, что обеспечивает сопоставимость потребления AWS и Azure на единой иерархии сервисов.
